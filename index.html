Practical AI Agent Design

The Practical AI Agent Framework

Design Principles for Building AI Agents That Deliver Real-World Outcomes

Framework Draft v1.0
A practical framework and set of design principles for architecting AI agents using four foundational pillars: Identity, Knowledge, Capabilities and Execution.

Introduction

Over the past year, AI Agent has become one of the most overloaded terms in software. Every week introduces another framework, orchestration library, or product claiming to simplify agent development. Most conversations quickly move toward prompts, reasoning models, vector databases, MCP servers, or orchestration frameworks. These are important implementation choices. However, they rarely answer a much more fundamental question.

What does an AI agent actually need in order to reliably complete real-world work?

While helping a colleague think through agent design, I found myself sketching a simple flowchart to answer exactly that question. The deeper we discussed it, the more I realised the conversation had very little to do with prompts or models. Instead, it sounded remarkably similar to onboarding a new employee.

If you hired someone today to perform a specific job independently, you wouldn't start by handing them a prompt. You would first define their role, teach them what they need to know, provide access to the right systems, establish how they should perform their work, and finally evaluate them based on the outcomes they deliver. Those same questions turned out to be equally useful when designing AI agents.

That observation became the foundation for what I now call The Practical AI Agent Framework.

Purpose of this Framework

This framework is not an attempt to redefine AI agents. Instead, it proposes a practical architectural model for designing agents that can reliably complete real-world work.

The Employee Analogy

One way to think about a practical AI agent is to imagine hiring a new employee. Regardless of the role, the onboarding process follows a remarkably consistent pattern. First, we define the role. Then we teach them what they need to know. We provide access to the systems required to perform their work. We establish how work should be carried out. Finally, we evaluate whether the intended outcome has actually been achieved. Designing an AI agent follows the same progression.

If you hired a new employee... When building an AI agent...
Define their role Identity
Teach them how the business works Knowledge
Give them access to company systems Capabilities
Explain how work should be performed Execution
Review completed work Verification

Mental Model

Throughout this article, think of the agent as a skilled employee being onboarded into a role. The four pillars simply organise everything that employee requires to perform their work successfully.

Design Philosophy

A practical AI agent should be the smallest system capable of reliably completing its intended outcomes.

This philosophy influences every architectural decision throughout the framework. The objective is not to build the most autonomous agent, nor the one with the greatest number of capabilities. Instead, the objective is to build only what is necessary for the agent to reliably achieve its intended outcomes.

Should every document become part of the prompt? Probably not. Should every agent have browser access? Only if the goal requires it. Should every problem be solved with an agent? Certainly not.

The challenge isn't building increasingly complex systems. The challenge is building systems that are complete, reliable, and intentionally designed.

The Practical AI Agent Framework

The framework is built around four architectural pillars. Each pillar answers a different design question. Together, they define the minimum architectural components required for an AI agent to reliably accomplish real-world work.

Pillar Question Answered
Identity Who am I?
Knowledge What do I need to know?
Capabilities What systems can I interact with?
Execution How do I accomplish work?

The pillars are intentionally independent. Identity is not a subset of Knowledge. Capabilities are not part of Execution. Knowledge is not simply Retrieval-Augmented Generation (RAG). Separating these concerns produces systems that are easier to design, reason about, and evolve over time.

Pillar One — Identity

Identity answers one of the most fundamental architectural questions: Who is this agent?

Identity defines the role the agent plays, the responsibilities it owns, the constraints it operates within, and the way it communicates. It establishes the behavioural boundaries that remain consistent across every task.

A well-designed Identity answers questions such as:

  • What responsibilities does this agent own?
  • What is it explicitly not responsible for?
  • How should it communicate?
  • How much confidence should it require before acting?
  • What high-level process should it generally follow?
  • What rules must always be respected?

Example Identity

You are a Senior Product Analytics Specialist.

Prioritize correctness over speed.
Never invent metrics.
Always explain assumptions.
Support conclusions using evidence.
If evidence is insufficient, clearly communicate what additional information is required.

Notice what is intentionally absent.

Database schemas. Event definitions. Metric documentation. Business rules.

Those are not part of Identity. They belong elsewhere.

Design Takeaway

Identity defines behaviour—not business knowledge. Think of it as the role description you would give a newly hired employee.

Pillar Two — Knowledge

Knowledge is often treated as a single concept. In practice, it is not.

Different kinds of information have different lifecycles, different retrieval patterns, and different purposes. Treating everything as "context" usually leads to bloated prompts, unnecessary token usage, and poorer reasoning.

Instead, the framework separates knowledge into three distinct categories.

Knowledge Type Purpose Typical Lifetime
Operating Knowledge Stable knowledge required to perform the role. Long-lived
Retrieved Knowledge Information retrieved only when needed. Per task
Runtime Context The evolving working state of the current task. During execution

Operating Knowledge

Operating Knowledge contains information that the agent depends on repeatedly while performing its role. It is not occasional reference material. It forms part of the agent's operational understanding.

Examples include:

  • Database schemas
  • Event definitions
  • Business metrics
  • API contracts
  • Query conventions
  • Domain terminology
  • Coding standards

Consider an Analytics Agent. Every investigation depends on understanding event definitions, metric calculations, and warehouse schemas. These are not documents that should be rediscovered every time through retrieval. They are foundational knowledge required for almost every task.

Retrieved Knowledge

Not every piece of information belongs inside the agent. Many information sources change frequently and should only be retrieved when relevant.

Examples include:

  • Internal documentation
  • PRDs
  • Wiki pages
  • PDFs
  • Customer records
  • Incident reports
  • Release notes

Retrieved Knowledge keeps the agent lightweight while still allowing it to access large and constantly changing information sources.

Runtime Context

Runtime Context is the agent's working memory while performing the current task. It is created continuously during execution.

Typical Runtime Context includes:

  • Conversation history
  • SQL results
  • Browser observations
  • API responses
  • Intermediate findings
  • Current hypotheses
  • Execution plans
  • Tool outputs

Runtime Context should not grow indefinitely. As execution progresses, the agent should continuously determine what remains useful, what can be summarized, and what can be discarded.

Design Takeaway

Architect knowledge according to its purpose and lifecycle. Stable Operating Knowledge, dynamically Retrieved Knowledge, and Runtime Context solve different problems and should be managed independently.

Pillar Three — Capabilities

Knowledge tells an agent what it knows. Capabilities determine what it can do.

A practical AI agent rarely creates value by producing text alone. It creates value by interacting with the systems required to complete a real-world job.

Instead of asking "Which tools should I connect?", the better design question is:

What actions must this agent be able to perform to reliably deliver its intended outcomes?

The answer depends entirely on the problem being solved. An analytics agent may require SQL execution and Python. A customer support agent may need access to a CRM and ticketing system. A shopping assistant may require browser automation and payment APIs. There is no universal capability set.

Examples of Capabilities

Capability Typical Operations
SQL Execute queries, inspect schemas, validate data.
Browser Navigate websites, authenticate, click, submit forms, download information.
Vision Interpret screenshots, UI elements, diagrams and documents.
OCR Extract text from scanned documents and images.
Python Analysis, statistics, visualisation and computation.
Internal APIs Create records, update systems, trigger workflows.
Messaging Send email, Slack or Teams notifications.

When an Agent May Not Be Necessary

This framework intentionally begins with the user's goal. Sometimes, the analysis reveals that an agent is unnecessary.

If the task simply requires generating text from a stable prompt, requires no external interaction, performs no reasoning over changing information, and never needs to complete work beyond producing an answer, a reusable prompt or workflow may be sufficient.

Agents become valuable when they must reason, make decisions, interact with external systems, and complete multi-step work on behalf of a user.

Design Takeaway

Don't add capabilities because they exist. Add only those required to reliably deliver the intended outcome.

Pillar Four — Execution

Identity defines behaviour. Knowledge provides understanding. Capabilities enable action.

Execution brings them together.

Every task follows an execution loop. Although implementation details vary between frameworks, the underlying reasoning pattern remains remarkably consistent.

Step Purpose
Observe Understand the user's request and current state.
Reason Determine what information or actions are required.
Select Choose the knowledge and capabilities most appropriate for the current step.
Act Execute the selected capability.
Manage Runtime Context Update, summarise or discard information as execution progresses.
Verify Determine whether the intended outcome has actually been achieved.

The Importance of Selection

One of the least discussed aspects of agent design is selection.

At every step, the agent must decide:

  • Which knowledge is relevant?
  • Which capability should be used?
  • Which previous observations still matter?
  • Which information can be ignored?
  • Is enough evidence available to continue?

Better foundation models generally make better selections. They retrieve more relevant information, choose more appropriate capabilities, and avoid unnecessary actions. The surrounding architecture, however, determines what choices are available. Even the most capable model cannot select information or capabilities that were never provided.

Design Takeaway

Intelligence determines how well the agent makes decisions. Architecture determines what decisions it is able to make.

Design Principles

The four pillars describe the architecture of a practical AI agent. The following principles describe how that architecture should be applied. Together, they form a practical approach for designing agents that reliably complete real-world work.

Principle 1

Start with the Goal, Not the Model

Every agent begins with a user outcome. Before choosing a model, prompt, framework or orchestration library, clearly define the work the agent is expected to complete.

The goal determines the agent's Identity, Knowledge, Capabilities and Execution.

Principle 2

Design for Outcomes, Not Responses

Success is not measured by producing convincing text. Success is measured by reliably completing the intended work.

The response is only one step toward the outcome.

Principle 3

Identity Defines Behaviour

Identity establishes how the agent should think, communicate and operate. It defines behaviour. It should never become a container for business knowledge.

Principle 4

Architect Knowledge by Purpose and Lifecycle

Not all knowledge belongs in the same place. Separate stable Operating Knowledge, dynamically Retrieved Knowledge and evolving Runtime Context. Each serves a different purpose and should be managed independently.

Principle 5

Equip the Agent with the Capabilities Required to Deliver the Intended Outcomes

Capabilities should be selected because they are necessary, not because they are available. Every capability should directly contribute to accomplishing the user's goal.

Principle 6

Minimize Unnecessary Context While Preserving Reliable Outcomes

Every additional token consumes attention, cost and reasoning capacity. Continuously question whether each piece of context genuinely improves the agent's ability to complete the task.

A practical AI agent should be the smallest system capable of reliably completing its intended outcomes.

Principle 7

Verify Completion Before Declaring Success

Executing actions is not enough. The agent should determine whether the intended outcome has actually been achieved. If not, execution should continue.

Putting the Framework into Practice

From Architecture to a Working Agent

A framework becomes useful when it changes how we design systems in practice. The four pillars are not independent checkboxes. They work together to answer four fundamental questions:

Identity — What is this agent responsible for?

Knowledge — What does it need to know to do that job well?

Capabilities — What must it be able to do to complete the job?

Execution — How should it work through the task and verify the result?

Consider an analytics agent whose job is to investigate changes in a product metric and explain what happened.

Start with the outcome

The design should begin with the user's job, not with the model or the tools. Suppose the user asks:

"Analyse last month's retention drop, identify what changed, and send me the findings."

The desired outcome is not "generate an answer about retention." The agent is expected to complete an analytical investigation and deliver a useful result. That distinction changes the architecture.

Identity

The agent needs a defined responsibility. It might be an analytics agent responsible for investigating product metrics, following approved analytical practices, communicating uncertainty, and presenting findings clearly.

Its identity establishes the behavioural constraints within which it operates. It tells the agent what kind of work it is responsible for and how it should approach that work.

Knowledge

The agent then needs the knowledge required to perform that responsibility accurately. This is where the distinction between knowledge and retrieval becomes particularly important.

Knowledge Examples for an Analytics Agent
Operating Knowledge Table schemas, event definitions, metric definitions, business terminology, approved query patterns and analytical rules.
Retrieved Knowledge Relevant documentation, experiment details, product specifications, previous analyses or other information needed for the particular investigation.
Runtime Context The user's request, observations, SQL results, intermediate findings, decisions and other information currently needed to continue the task.

A vector database alone cannot provide all of this. Some knowledge must be consistently available because the agent cannot reliably perform its job without it. Other information can be retrieved when relevant. And the results of the agent's own work become part of the runtime context as the task progresses.

Capabilities

The agent now needs the ability to perform the work. For this example, that could include inspecting database schemas, generating and executing SQL, running calculations, accessing relevant product data, creating a report, and sending the final result.

These are not simply "tools added to an agent." They are capabilities required by the job.

If the agent cannot query the underlying data, it cannot independently investigate the retention drop. If it cannot deliver the resulting report, it cannot complete the user's requested outcome.

Execution

Finally, the agent needs a process for turning its identity, knowledge and capabilities into completed work.

01
Understand

Interpret the user's goal and determine what needs to be established.

02
Investigate

Use available knowledge and capabilities to gather the required evidence.

03
Act

Execute queries, calculations and other actions required by the investigation.

04
Verify

Check whether the evidence supports the findings and whether the requested work is actually complete.

05
Deliver

Communicate the findings and complete the requested action.

The important point is that the agent is not merely producing a sequence of model responses. It is progressing toward a completed outcome.

The test is simple: remove one of the pillars and ask whether the agent can still reliably complete the job. If the answer is no, that pillar is part of the agent's practical architecture—not an optional feature.

Architecture vs Implementation

Design the Architecture Before Choosing the Tools

AI agent development is increasingly surrounded by frameworks, protocols, SDKs and implementation patterns. These are useful, but they can make it easy to confuse the implementation of an agent with the architecture of the agent itself.

The Practical AI Agent Framework deliberately separates the two.

Architecture

What the agent needs

  • Identity
  • Knowledge
  • Capabilities
  • Execution

These describe the enduring requirements of the agent's job.

Implementation

How the agent is built

  • Prompt engineering
  • RAG and retrieval systems
  • MCP
  • Agent SDKs
  • Orchestration frameworks
  • Custom code

These are mechanisms for realizing the architecture.

For example, MCP can provide a useful mechanism for exposing capabilities. A retrieval system can provide dynamically retrieved knowledge. An agent SDK or orchestration framework can manage execution. None of these, individually, defines what the agent is.

The same architecture can therefore be implemented using very different technologies.

Where does a harness fit?

The term harness is increasingly used to describe the software layer surrounding a model that manages things such as context assembly, tool calls, state, retries, model routing, logging and other execution concerns.

In this framework, a harness is an implementation layer, not a fifth pillar. Different harnesses can implement the same underlying agent architecture.

Architecture defines what the agent needs to do its job. Implementation defines how those requirements are realized.

This distinction matters because implementation technologies will continue to change. Today's preferred SDK, protocol or orchestration framework may look very different in a few years. A well-designed agent architecture should not need to be reinvented every time the tooling changes.

Design the architecture first. Then choose the implementation that best realizes it.

Conclusion

Build Agents Around the Work They Need to Complete

The term AI agent is becoming increasingly broad. A system prompt, a knowledge base, a tool call, an orchestration framework, and a fully autonomous software system can all be described using the same word.

The Practical AI Agent Framework offers a simpler way to reason about the problem: start with the job the user needs completed, then design the system around what is required to reliably complete it.

01 Identity

Defines who the agent is, what it is responsible for, and how it should behave.

02 Knowledge

Provides the stable, retrieved and runtime information required to perform the job.

03 Capabilities

Gives the agent the ability to observe and change the systems required to complete the work.

04 Execution

Turns the agent's reasoning and capabilities into a process that progresses toward a verified outcome.

The framework is intentionally technology-agnostic. Models, prompts, retrieval systems, protocols, SDKs and harnesses will continue to evolve. The underlying architectural questions remain.

What is this agent responsible for? What does it need to know? What does it need to be able to do? And how will it know that the work is actually done?

A practical AI agent should be the smallest system capable of reliably completing its intended outcomes.

More capabilities are not inherently better. More context is not inherently better. More complexity is not inherently better. The goal is to build enough of the right system to reliably do the work.

This framework is intended as a starting point rather than a final definition. As agent architectures evolve, these principles should be tested, challenged and refined through real implementations and practical experience.
